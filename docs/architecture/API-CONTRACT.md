# GIZER NBA — API contract (v1)

Base path `/api/v1`. JSON only. The web app calls the API same-origin (Next.js rewrites `/api/v1/*`
to the API container). OpenAPI is generated by FastAPI at `/api/v1/openapi.json` (owner only in production).

## Conventions

* Auth: HttpOnly session cookie `gizer_session` set by `POST /auth/login`. Every endpoint except
  `/health`, `/health/ready`, `/auth/login` requires it → `401 {"error":{"code":"unauthenticated","message":…}}`.
* Mutations (`POST`) must send `X-CSRF-Token: <csrf>` (value from `/auth/login` or `/auth/me`) → else `403`.
* Errors always: `{"error": {"code": string, "message": string}}`.
* Timestamps are ISO-8601 UTC. Dates are `YYYY-MM-DD` in America/New_York. Display times in ET.
* Probabilities are floats 0–1. `evidence_score` is an integer 0–100 measuring **evidence quality**, never a probability.
* `null` means "not available" — the UI must show an explicit unavailable state, never a placeholder number.
* Classifications: `high_confidence | standard | watchlist | insufficient_evidence | rejected | invalidated`.
  "Qualified" = `high_confidence` or `standard`.

# V3 additions — player intelligence, props, lineups

Unless stated, fields may be `null` (= not available; render "—", never 0).
Stat keys used everywhere: `min, pts, reb, ast, fg3m, stl, blk, tov, pra, pr, pa, ra`
(pra = points+rebounds+assists, pr = points+rebounds, pa = points+assists, ra = rebounds+assists).
Prop market keys: `player_<stat>` for `pts, reb, ast, fg3m, stl, blk, tov, pra, pr, pa, ra`.

# Core Intelligence V1 additions — Kalshi, minutes, availability events

Kalshi prices are dollars per $1 contract (0–1). `price` = bid/ask midpoint when both exist, else last trade.
Classification gains `stale` (only freshness checks failed). Edition `kind` gains `update` (published when a material
availability or lineup change is detected). `Selection.evidence`-derived field `Selection.contract: string|null`
is NOT exposed; use `book === "Kalshi"` and the Kalshi endpoints.

## JARVIS (assistant, memory, briefings, AI budget) — added 2026-11-26

All routes are under `/api/v1`, need a session, and state-changing ones need `X-CSRF-Token`. Only the `owner`
role may start conversations, send messages, edit memory, run briefings or view/change the AI budget.

### State and discovery
* `GET /jarvis/state` → `{state, message, models:{standard,deep,light}, models_verified, budget:{spent_usd, remaining_usd,
  usable_usd, today_usd, state}, daily_cap_usd, lifetime_cap_usd}`. `state` is one of `ready`, `provider_unavailable`
  (no key / provider down), `budget_limited`, `paused`. "processing" and "error" are per-request states the UI derives
  from the stream. Never show the assistant as thinking unless a request is in flight.
* `GET /jarvis/suggestions?game_id&player_id&ticker&selection_id&combo_id` → `{context, items:[{label, text}]}`
  (context-specific suggestions first). Texts starting with `/` are answered from stored data without a model.
* `GET /jarvis/tools` → `{items:[{name, label, group, description, writes}], total, note}`.

### Conversations
* `GET /jarvis/conversations?limit=` → `{items:[{id, title, context, created_at, updated_at}]}` newest first.
* `POST /jarvis/conversations` body `{context?}` → conversation. `context` = `{game_id?, player_id?, ticker?,
  selection_id?, combo_id?, date?, page?}`; unknown ids are dropped server-side. The stored/echoed context is resolved:
  `{game:{game_id,label,date}, player:{player_id,name,team}, kalshi_market:{ticker,title}, selection:{record_id},
  combination:{record_id}, date, page}`.
* `GET /jarvis/conversations/{id}` → conversation + `messages:[{id, role, text, model, stop_reason, sources:[{tool,label,args}],
  cost_usd, created_at, tool_calls:[{name,input}]}]` + `tool_activity:[{tool,label,args,ok,error,ms,truncated,at}]`.
  Assistant `text` is Markdown (headings, bullets, tables, bold).
* `POST /jarvis/conversations/{id}/delete` → `{deleted:true}`. (The API uses GET and POST only.)
* `POST /jarvis/conversations/{id}/messages` body `{text (1..8000), mode: "standard"|"deep", context?}` →
  **`text/event-stream`**. It is a POST, so read it with `fetch` + `ReadableStream` (not `EventSource`). Each event is one
  line `data: {json}` followed by a blank line. Event `type`s, in order of appearance:
  * `status` `{state:"processing", routing:{handler, mode?, tool?, reason}, model?}`
  * `tool_start` `{id, tool, label, args}` — a real tool call began. Show `label` (e.g. "Inspecting the injury report").
  * `tool_end` `{id, tool, ok, ms, error?, truncated?}`
  * `text` `{delta}` — append to the answer.
  * `usage` `{cost_usd, total_cost_usd, input_tokens, output_tokens, cache_read_tokens}` — once per model request.
  * `done` `{message_id, model, cost_usd, sources:[{tool,label,args}], stop_reason}` — terminal.
  * `error` `{code, message, state?, message_id?, cost_usd?}` — terminal. Codes include `not_configured`, `lifetime_cap`,
    `daily_cap`, `allocation`, `request_too_large`, `paused`, `provider_unavailable`, `auth`, `conversation_too_long`.
    Show `message` verbatim; set the status indicator from `state`.
  `model` is a model id, or `"deterministic"` for slash commands. `mode:"deep"` uses the Opus allocation; make it an
  explicit owner toggle, off by default, labelled as costing more.

### Memory
* `GET /jarvis/memory?category=&q=&limit=` → `{items:[{id, category (research|operational|preference|conversation),
  status (verified|hypothesis|preference), subject_type, subject_id, text, sources[], observed_on, created_by, created_at}]}`
* `POST /jarvis/memory` body `{category, text, status?, subject_type?, subject_id?}` → item. `POST /jarvis/memory/{id}/delete` → `{deleted:true}`.

### Briefings and events
* `GET /jarvis/briefings?kind=&limit=` → `{items:[{id, kind (overnight|morning|midday|pregame|postgame), date, text,
  generator ("deterministic" or a model id), cost_usd, created_at}]}`
* `POST /jarvis/briefings/run` body `{kind}` → `{created, id?, generator?, cost_usd?, reason?}`
* `GET /jarvis/events?kind=&limit=` → `{items:[{id, kind, severity (info|notice|alert), title, detail, game_date, occurred_at}]}`

### AI budget (owner)
* `GET /admin/ai-budget` → `{policy:{lifetime_cap_usd, suspend_at_usd, daily_cap_usd, allocations:{sonnet,haiku,opus,dev},
  per_request_cap_usd:{...}, paused, buffer_released, notifications, updated_at, updated_by}, spent_usd, pending_usd,
  remaining_usd, usable_usd, today_usd, month_usd, state (ok|budget_limited|paused), checkpoints:[{pct, usd, reached}],
  buckets:[{bucket, allocation_usd, used_usd}], by_model:[{key, requests, usd, input_tokens, output_tokens,
  cache_read_tokens, cache_write_tokens}], by_task:[…], by_agent:[…], requests, input_tokens, output_tokens,
  cache_read_tokens, cache_write_tokens, cache_savings_usd, avg_usd_per_day, est_days_remaining,
  daily:[{date, requests, usd}], prices:{model:{in,out,cache_read,cache_write}}, notes:[…], assistant:{…/jarvis/state}}`
* `POST /admin/ai-budget` body: any of `{lifetime_cap_usd, suspend_at_usd, daily_cap_usd, allocations, per_request_cap_usd,
  paused, buffer_released, notifications}` → policy. `422` if the lifetime cap would exceed the authorised $100 or the
  allocations exceed it. `paused:true` is the emergency AI pause; `notifications:false` stops proactive briefings while
  data collection continues.
* `GET /admin/ai-budget/requests?limit=` → `{items:[{id, at, status (reserved|settled|released|assumed), bucket, model,
  task, reserved_usd, actual_usd, input_tokens, output_tokens, cache_read_tokens, cache_write_tokens, attempt, routing,
  error, conversation_id}]}`

### JARVIS image attachments (added 2026-11-26)
* `POST /jarvis/conversations/{id}/messages` body gains `images: [{media_type, data}]` (0 to 3). `media_type` is one of
  `image/png`, `image/jpeg`, `image/webp`, `image/gif`; `data` is base64 without a `data:` prefix, at most about 1.5 MB of
  image each (2,100,000 base64 characters). `text` may be empty when at least one image is attached. Slash commands
  are ignored when an image is attached (the message goes to the model).
* Terminal `error` code `invalid_image` carries a message to show verbatim (wrong type, too large, unreadable, too many).
  A body over the limits is a `422` JSON error before any stream starts.
* Message objects gain `images: <count>`. The bytes are served by `GET /jarvis/messages/{message_id}/images/{index}`
  (owner's own conversations only; `index` from 0), suitable for an `<img src>`.
* The client must downscale before upload: longest side at most 1568 px, re-encoded as JPEG (quality about 0.85) unless the
  original is already small, so each image is well under the limit.
* New tool label that can appear in the stream: "Evaluating the combination" (`evaluate_combination`).

## GIZER LIVE (observed in-game data) — added 2026-11-26

All under `/api/v1`, session required; follow/milestone writes need the owner role and CSRF. GET and POST only.
Everything is an **observation our server polled** (about every 15 s while a game is in progress): never call it
real-time. Every game-shaped object carries freshness: `observed_at`, `provider_updated_at`, `age_s`, `stale`
(true when a game in progress has not been observed for 90 s), `feed` (`ok`|`stale`|`not_started`). When `stale`
is true show "Delayed — last update <time>" and keep showing the last values. A `null` number means the source has
not published it: show "—", never 0.

### Scoreboard
`GET /live/scoreboard?date=YYYY-MM-DD` (default today ET) → `{date, prev, next, today, live_count, server_time, poll_note,
games:[GameRow]}`. `GameRow` = `{game_id, label, game_date, tipoff_utc, venue, status, status_label, period,
period_label ("Q1".."Q4","OT","2OT",""), clock (only while live), home:{team_id, abbr, name, score, linescores:[..]},
away:{…}, version, followed, favorite_team, …freshness}`.
`status` ∈ `scheduled|live|halftime|end_period|overtime|final|delayed|postponed|suspended|cancelled`. A game is `live`
only when the provider says so. Followed games/favourite teams sort first, then live, halftime, scheduled, final.
`GET /live/games` is the same.

### Game centre
* `GET /live/games/{id}` → `GameRow` + `{mode: "pregame"|"live"|"final"|status, team_stats, leaders:{home:{pts,reb,ast:{player_id,name,value}|null},away},
  momentum:{lead_changes, ties, largest_lead:{home,away}, runs:[{team:"home"|"away", points, start_s, end_s}], note, points:<count>},
  last_plays:[Play] (newest first, 8), plays_count, summaries:[{kind:"q1"|"half"|"q3"|"final", text, created_at}], poll_note, notes[]}`
* `GET /live/games/{id}/boxscore?sort=<column>&order=asc|desc` → `{game_id, status, period, available, home:{team_id, abbr, name,
  players:[BoxRow], totals:{…}}, away:{…}, notes[], …freshness}`. `BoxRow` = `{espn_athlete_id, player_id|null, team_id, name,
  position, jersey, headshot_url, starter, role:"starter"|"bench"|null, dnp, ejected, on_court:true|false|null, minutes, pts, reb, ast,
  stl, blk, tov, pf, fgm, fga, fg3m, fg3a, ftm, fta, oreb, dreb, plus_minus, pra, pr, pa, ra, fg_pct, fg3_pct, ft_pct,
  true_shooting_pct, foul_trouble:true|false|null, pregame:{proj_min, pts, reb, ast, fg3m, published_at}|null}`.
  `on_court: null` means not determinable: show nothing, not "bench". `player_id: null` means no profile link.
  Sort client-side as well (every column sortable); `sort` is offered for convenience.
* `GET /live/games/{id}/play-by-play?filter=all|scoring|fouls|substitutions&team_id=&player_id=&after_sequence=&order=desc|asc&limit=&offset=`
  → `{game_id, total, items:[Play], note, …freshness}`. `Play` = `{event_id, sequence, period, clock, elapsed_s, team_id,
  team_side:"home"|"away"|null, kind (made|missed|free_throw|rebound|turnover|foul|substitution|timeout|period|review|jumpball|other),
  type_text, text, scoring, score_value, home_score, away_score, player_ids[], provider_at, ingested_at, corrected}`.
  `text` is the source's wording; never add commentary. Use `after_sequence` to fetch only new plays.
* `GET /live/games/{id}/rotations` → `{game_id, status, period, elapsed_s, home:{team_id, abbr, determinable, problems[], note,
  players:[{espn_athlete_id, player_id, name, starter, role, on_court, stints:[{start_s, end_s|null}], minutes_by_period:{"1":..},
  minutes, pf, foul_trouble, proj_min, minutes_vs_projection}]}, away:{…}, notes[]}`. When `determinable` is false show the `note`
  and no timeline for that team. Timeline x-axis is game seconds: quarters are 720 s, overtime periods 300 s.
* `GET /live/games/{id}/team-stats` → `{game_id, home:{team_id,abbr}, away:{…}, available, items:[{key, label, home, away,
  home_value, away_value}], not_published[]}`. `home`/`away` are the published strings (e.g. "24-50"); `*_value` drive the bars.
* `GET /live/games/{id}/momentum` → `{points:[{t, period, home, away, diff}], lead_changes, ties, largest_lead, runs, note}`
  (`diff` = home − away after each scoring event). Label it "Score progression (observed)". No win probability exists.
* `GET /live/games/{id}/stream` → `text/event-stream` (GET, so `EventSource` works with cookies): `data: <GameRow json>` whenever
  the game's `version` changes and at least every ~15 s; comment lines `: keep-alive` between; `event: end` after 5 minutes —
  reconnect. On each `data`, refetch whichever tab is open if `version` increased. On error use backoff (1 s, 2 s, 5 s, 10 s)
  and show "Reconnecting…"; fall back to polling `GET /live/games/{id}` every 15 s if the stream cannot be opened.
